Application Debugging using IntelliJ IDEA (Beginner → Advanced Notes)

Java IntelliJ IDEA Breakpoints Step Into/Over/Out Advanced Debugging

These notes explain how to debug a Java application in IntelliJ IDEA using a real mini project example (EmployeeApp → Service → Repository). You’ll learn what each debug action means, when to use it, and how to debug like a pro.

1) What is Debugging?

Debugging is the process of finding and fixing issues by running the program in a controlled way and checking values (variables/objects) step-by-step.

Key idea: A debugger lets you pause the program at specific lines and inspect the “current state” (variables, call stack, objects in memory).

What you can do in IntelliJ Debugger

  • Pause execution at a line (breakpoint)
  • Run line-by-line (Step Over/Into/Out)
  • Check variables in the Variables panel
  • Use Evaluate Expression to run small expressions without changing code
  • Set Conditional Breakpoints and Exception Breakpoints
  • Debug multiple threads and inspect the Call Stack

Quick Shortcut Cheat Sheet

Run & Debug

  • Debug: Shift + F9
  • Run: Shift + F10
  • Stop: Ctrl + F2

Stepping

  • Step Over: F8
  • Step Into: F7
  • Step Out: Shift + F8
  • Resume: F9
Pro tip: If shortcuts differ (Mac/Linux), open: Settings → Keymap and search “Step Over”, “Step Into”, etc.

2) Getting Started: Debug an Application in IntelliJ

Step A — Place a Breakpoint

  • Open the file you want to debug (example: EmployeeApp.java).
  • Click on the left gutter (left side of line numbers) to add a red dot.
  • This red dot = Breakpoint.

Step B — Start Debug Mode

  • Right-click your main class → Debug
  • OR use Shift + F9

Step C — Understand the Debug Window

  • Threads: shows running threads (usually “main” for a simple app)
  • Frames / Call Stack: shows how you reached current line (which methods called which)
  • Variables: shows values of local variables, parameters, and fields
  • Console: standard output and logs
Important: When the program pauses on a breakpoint, it means the program state is frozen at that exact moment, and you can inspect everything safely.

3) Basic Debugging Techniques

3.1 Breakpoints (Debug Points)

A breakpoint pauses the program before executing that line. This lets you see what values exist right now.

Where to place breakpoints (using your Employee project)

  • At the start of main() to inspect initial values like args and logger configuration.
  • Before service calls to capture input data.
  • Inside service/repository methods to see how data changes.
Suggested breakpoints for your flow:
1) In EmployeeApp.main() at the line that logs “Log4j2 is working…”, and at List<Employee> employees = service.getAllEmployees();
2) In EmployeeServiceImplementation.addEmployee() on employeeRepository.save(employee);
3) In EmployeeRepositoryImpl.save() on db.put(employee.getId(), employee);
This shows how the object flows Main → Service → Repository.

3.2 Step Over vs Step Into vs Step Out

✅ Step Over (F8)

Executes the current line and moves to the next line in the same method. If the line calls another method, it runs that method without entering it.

Use Step Over when you trust the called method and you only want to move forward quickly.

✅ Step Into (F7)

Enters the method that is being called on the current line, so you can debug inside it.

Use Step Into when you suspect a bug is inside the called method (service/repository).

✅ Step Out (Shift + F8)

Runs the remaining lines of the current method and pauses when you return back to the caller. Useful when you entered a method but you don’t want to step through every line.

Common fresher mistake: repeatedly using Step Into and getting stuck inside JDK/library code. Use Step Over or Smart Step Into (see Advanced section) to avoid that.

4) Debugging with Your Actual Code (EmployeeApp Example)

4.1 Understand the flow

Your main method does:

  • Create Repository: new EmployeeRepositoryImpl()
  • Create Service: new EmployeeServiceImplementation(repository)
  • Add Employees: service.addEmployee(new Employee(...))
  • Fetch list: List<Employee> employees = service.getAllEmployees();
  • Find by id, delete, print again

4.2 “How to see the value BEFORE calling service, and AFTER calling service?”

  1. Breakpoint 1: put breakpoint on the line service.addEmployee(new Employee(1, ...)) in EmployeeApp.
  2. When paused, look at Variables:
    • service → expand it → confirm employeeRepository is not null.
    • Hover your mouse on service or use Evaluate.
  3. Now press Step Into (F7) to enter addEmployee().
  4. Breakpoint 2: inside addEmployee(), pause on employeeRepository.save(employee);
  5. Inspect:
    • employee parameter → expand → see id/name/department/salary.
    • Check validations: if salary <= 0, it throws exception.
  6. Press Step Into (F7) again to enter repository save().
  7. Breakpoint 3: on db.put(employee.getId(), employee);
  8. Inspect:
    • Expand db (HashMap) → before execution it may be empty.
    • Step Over this line → now expand db again → you’ll see the new entry.
  9. Now press Step Out (Shift+F8) to return to service, then Step Out again to return to main.
  10. Repeat for next employees and you’ll see how the in-memory DB grows.
Best place to verify “list after service call”:
Put a breakpoint on List<Employee> employees = service.getAllEmployees(); in main. Then use Step Over and expand employees in Variables. You’ll see the full list.

4.3 Example: Debug “Division by zero” using Calculator

In your Calculator class, divide() throws ArithmeticException when divisor is 0. This is a perfect case to use an Exception Breakpoint. 

// Calculator.divide()
public double divide(final int a, final int b) {
  if (b == 0) {
    throw new ArithmeticException("Division by zero not allowed");
  }
  return (double) a / b;
}
How to debug it:
1) Add an Exception Breakpoint for java.lang.ArithmeticException
2) Run Debug
3) When exception occurs, IntelliJ pauses at the exact throw line.

5) Advanced Debugging (What it means + How to do it)

“Advanced debugging” means using debugger features that help you debug faster in real projects: large codebases, many conditions, multi-threading, hard-to-reproduce bugs, performance issues, etc.

5.1 Conditional Breakpoints

  • Stops only when a condition is true (example: stop only when employeeId == 2).
  • How: Right-click breakpoint → add condition.
// Example condition (in EmployeeRepositoryImpl.save or service.addEmployee)
employee.getId() == 2
Use this to avoid stopping 100 times inside loops.

5.2 Logpoints (Print without changing code)

  • A “breakpoint” that doesn’t stop. It just logs a message when hit.
  • How: Right-click breakpoint → uncheck “Suspend” and enable “Log message”.
This is amazing when you want to trace values but don’t want to add System.out.println everywhere.

5.3 Smart Step Into

  • If a line calls multiple methods, Smart Step Into lets you choose which one to enter.
  • How: Use “Smart Step Into” from the Debug toolbar (shortcut varies by keymap).

5.4 Evaluate Expression & Watches

  • Evaluate Expression: run any Java expression in the current context.
  • Watch: keep an expression monitored as you step through code.
// Examples you can evaluate during debug in EmployeeApp:
employees.size()
service.getEmployeeById(2)
repository.findAll()

5.5 Exception Breakpoints (Stop when an exception happens)

  • Stop on thrown exceptions like NullPointerException, IllegalArgumentException, etc.
  • How: Breakpoints view → “+” → Java Exception Breakpoint.
  • You can also stop only on uncaught exceptions.

5.6 Drop Frame (Re-run a method without restarting)

  • Moves the execution back to the start of the current method (like “rewind”).
  • How: In Call Stack → right-click frame → “Drop Frame”.
  • Useful when you want to rerun a method after changing a variable in debug.

5.7 Set Value (Change variable while paused)

  • Right-click a variable → “Set Value…”
  • Example: change salary from 0 to 50000 and continue.
Warning: Changing runtime values is for debugging only. Don’t treat it as a permanent fix.

5.8 Force Return / Throw Exception

  • Force a method to return a value immediately (useful for testing alternate paths).
  • Force-throw an exception to test error handling.

5.9 Debugging Collections and Objects (Deep inspection)

  • Expand objects (Employee) and collections (List/Map) in Variables.
  • Use “View as…” (if available) to render structures nicely.
  • For HashMap (your fake DB), expand keys/values to verify insertion and deletion.

5.10 Multi-thread Debugging

  • In complex apps, multiple threads run (web servers, async tasks).
  • Debugger shows thread list → you can pause/resume specific threads.
  • Use this to find race conditions or deadlocks.
In your current console app, mostly only the “main” thread runs, so thread complexity is low. But these skills matter for Spring Boot apps.

6) Debug Like a Corporate Developer (Workflow)

  1. Reproduce the issue (same input, same steps)
  2. Pick the smallest entry point (usually controller/main method)
  3. Add 2–3 strategic breakpoints (before call, inside call, after call)
  4. Use Step Over for normal flow, Step Into only when needed
  5. Inspect values + call stack to understand “how we reached here”
  6. Add conditional breakpoints/logpoints when loops or many calls exist
  7. Use Evaluate/Watch for quick checks without code change
  8. Fix the root cause, then rerun & confirm
Gold rule: Debugger is not only for errors. It is also for learning code flow and validating assumptions.
